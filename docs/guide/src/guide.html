1. The project in one page

What it is. A CPU scheduler that predicts how long each process will run on its next CPU burst, and uses that prediction twice: to decide which process runs next, and to decide how long it may run (the time quantum). The time quantum is recalculated continuously while the system runs, instead of being fixed by hand.

Why. SJF gives the lowest average waiting time but needs the next burst length, which nobody knows in advance. The usual estimate, exponential averaging, reacts slowly when a process changes behaviour. Round Robin needs a quantum, and the textbook rule for choosing one (about 80% of bursts should finish within one quantum) is normally applied once by a person and never revisited.

How it was built. Everything is in Python. A discrete-event simulator models one CPU with processes that alternate CPU bursts and I/O. Eleven scheduler configurations run on exactly the same workloads: FCFS, SJF, SRTF, Round Robin (four quanta), MLFQ, an oracle that knows the future, and two versions of the proposed scheduler. A gradient-boosting model, trained on generated process histories, predicts the next burst.

Result in one line. On the mixed workload, the realistic case, the proposed scheduler cuts average waiting time by 27% compared with SJF using exponential averaging. It is better on all 10 seeds, closes 54% of the gap to the oracle, lowers the worst-case wait by 23%, and uses 61% fewer context switches than Round Robin with a 5 ms quantum. It does not help on workloads made only of short random bursts, and the documents say so openly.

What happens when the prediction is wrong. A burst that runs longer than predicted keeps its short estimate, so with time slicing it returns to the ready queue looking short again and again. An overrun guard fixes this: once a burst clearly outruns its prediction, its estimated time left becomes max(prediction, 0.25 × CPU time used). On the intentionally adversarial W7 bait-and-switch workload the guard cuts the average wait by 21.5% and interactive waiting by 92%, with no significant change on W1–W5. MLFQ still has a lower average wait on W7, and a second idea, persistent ageing, made average waits worse and was not kept. Every main claim is checked with paired statistical tests.

3. Architecture

The key design decision is that the simulation engine never makes a scheduling decision. It owns the clock, the event queue and the process control blocks (PCBs), and whenever a decision is needed it calls the policy interface. Any scheduler that implements the interface can be plugged in. This guarantees that every scheduler is tested on identical arrivals, bursts, I/O times and switch costs, so differences in the results come only from the decisions.

Inside the adaptive scheduler, the feature extractor turns a process's history into 12 numbers, the burst predictor estimates the next burst, the classifier labels the process type, the ready-queue ordering applies the ageing formula (and, in Adaptive-ML-G, the overrun guard), and the quantum controller recomputes the time slice. When a burst completes, the feedback loop records the error and stores the example for refitting. After a run, the metrics collector computes all measures and the analysis step produces tables and figures.

4. What happens during one simulation run

Following one process through the engine (scheduler/engine.py) makes the whole system easy to understand:

  1. Start. The engine puts an ARRIVAL event for every process into a priority queue ordered by time.
  2. Arrival. When an arrival event is popped, the process's first burst is loaded (_start_burst) and it joins the ready queue (_make_ready). The policy's on_ready hook runs; for the adaptive scheduler, this is where the next burst is predicted.
  3. Preemption check. For preemptive policies (SRTF, MLFQ, oracle), the engine asks should_preempt whether the newcomer should interrupt the running process.
  4. Dispatch. After all events at the current instant are handled, if the CPU is idle the engine calls select to pick a process and time_slice to get its quantum. If the process differs from the last one, a 0.1 ms switch cost is charged. A SLICE_END event is scheduled at start + min(quantum, remaining burst).
  5. Slice end. If the burst is finished, on_burst_complete runs (feedback loop), and an IO_DONE event is scheduled after the I/O time. If the quantum ran out instead, on_quantum_expired runs and the process goes back to the ready queue.
  6. I/O done. The next burst is loaded and the process becomes ready again. Steps 2–6 repeat.
  7. Finish. After the last burst, the completion time is recorded. When the event queue is empty, the engine returns a SimResult with all PCBs, the timeline and the switch count.

Two details keep the engine correct. First, all events at the same time are processed before a decision is made, so processes arriving together are all considered (this is what makes the SJF example give exactly 3 ms). Second, when a slice is cut short by preemption, its pending SLICE_END event is cancelled with a token, so it cannot fire later by mistake.

6. The prediction model

6.1 Features

For every process, 12 features are built only from bursts and I/O waits that have already finished, all of it information the operating system already has: the last 5 burst lengths, the mean and standard deviation of past bursts, the exponential average estimate, the last and mean I/O wait, the number of bursts completed, and the change between the last two bursts. A test checks that changing a process's future bursts does not change its features, which proves there is no leakage.

6.2 Training

train_models.py generates 2,000 processes (500 of each type) from seeds 1000–1004, which are never used in the experiments. Because the features depend only on a process's own history, the dataset (45,389 rows, one per burst) is built directly without running the simulator. It is split 75/25 by process, so no process appears in both training and testing.

ModelMAE (ms)Latency per predictionNotes
Exponential averaging12.36~0The baseline to beat
Ridge regression14.820.08 msA single linear rule cannot fit all process types
Gradient boosting12.590.50 msLarge bursts dominate the squared error
Gradient boosting, log target10.620.50 msChosen: 14% lower error, better for every type

Selection rule: lowest error within a 1 ms latency budget, with Ridge preferred if within 5%. Training on log(burst) helps because burst lengths range from 0.05 ms to hundreds of ms. A logistic regression classifier (macro-F1 0.94) is also saved; a random forest scored 0.94 but was 20 times slower.

Why single-threaded? scikit-learn normally uses all CPU cores, but the simulator asks for one prediction at a time. Starting threads for one row made each prediction take 3.7 ms instead of 0.5 ms, so scheduler/__init__.py sets OMP_NUM_THREADS=1.

6.3 Feedback loop

When a burst finishes, observe() compares it with the prediction, logs the error (this is how prediction MAE is reported for every run) and adds the example to a rolling buffer of 4,000. Every 2,000 new examples the model is refitted on 10,000 offline rows plus the buffer. The quantum controller also keeps the last 200 ratios actual / predicted.

7. The adaptive scheduler in detail

7.1 Who runs next

P = (predicted time left in the burst) − β × (time waited in the ready queue)

The lowest P runs. Predicted time left is the prediction minus the CPU time already received in this burst; if the burst has already run longer than predicted, the original prediction is used again. Example: with β = 0.1, process A predicted at 50 ms that has waited 400 ms has P = 50 − 40 = 10; process B predicted at 5 ms that has waited 10 ms has P = 5 − 1 = 4, so B runs. If A had waited 600 ms, P = −10 and A would run first. With β = 0 the scheduler is exactly SJF (checked by a test). The final value β = 0.03 was picked by tune_beta.py.

The overrun guard (Adaptive-ML-G). Falling back to the original prediction is exactly what goes wrong when a long burst was predicted as short: after every quantum it returns with the same short estimate. The guard keeps the normal rule until the burst has run longer than prediction × r, where r is the median of the last 200 ratios actual/predicted (at least 1). After that, time left = max(prediction, 0.25 × CPU time used). Example: predicted 1.2 ms, already ran 40 ms: time left 10 ms instead of 1.2 ms, so a new interactive burst predicted at 5 ms goes first; after 200 ms the burst looks like 50 ms. It never makes a burst look shorter than its prediction. c = 0.25 was chosen on seeds 100–102.

7.2 How long it runs

Every 50 decisions, the quantum controller takes the predictions of the bursts that became ready in that period, multiplies each by every recent error ratio, takes the 80th percentile, clamps it to 1–100 ms, and smooths it: q = 0.3 × qnew + 0.7 × q.

Worked example (I/O-bound workload). Bursts average 2 ms, so almost every prediction is about 2 ms. If the quantum used the raw predictions, the 80th percentile would be about 2 ms, too small, because 20% of real exponential bursts with mean 2 ms are longer than 3.2 ms. The recent ratios actual/predicted are spread widely, and for exponential bursts their 80th percentile is about 1.6, so the 80th percentile of 2 × ratios is about 3.2 ms, matching the textbook rule. Starting from q = 10 ms, smoothing gives 0.3 × 3.2 + 0.7 × 10 = 7.96 ms, then 6.5, 5.5, and so on, settling near 3.5 ms. This error-ratio fix was added after the first version produced quanta that were too small on W2 and W3.

Class modulation. The classifier labels the processes seen in the epoch; the percentile becomes 80 + 10 × (fraction CPU-bound − fraction interactive), limited to 50–95. Interactive mixes get a smaller quantum (faster response), CPU-bound mixes a larger one (fewer switches).

8. Experiments and evaluation pipeline

Workloads. Four process types: CPU-bound (lognormal bursts, median 100 ms, 3–8 bursts), I/O-bound (exponential, mean 2 ms, 20–60 bursts), interactive (exponential, mean 5 ms, 10–40 bursts) and phase-changing (I/O-bound then CPU-bound). Six profiles of 200 processes at 85% CPU load: W1 CPU, W2 I/O, W3 interactive, W4 mixed (40/30/20/10%), W5 phase-changing, W6 = W4 at 3× arrival rate.

Configurations (11). FCFS, SJF-EMA, SRTF-EMA, RR-2, RR-5, RR-10, RR-20, MLFQ, Oracle, Adaptive-EMA (our scheduler with the classical predictor) and Adaptive-ML (our scheduler).

Runs. 6 workloads × 11 configurations × 10 seeds = 660 paired runs, plus an ablation (120 runs), sweeps of β, p and E (130 runs) and switch costs of 0.05/0.1/0.5 ms (150 runs). The runs are spread over 9 worker processes and take about 4.5 minutes.

Fairness of the comparison. Every policy sees the same seeds (paired comparison), the oracle gives a reference point, and expected outcomes (H1–H7) were written down before any experiment. 9. Robustness to prediction errors: the overrun guard, W7 and statistics

9.1 How much prediction quality matters

The noisy oracle gives the scheduler the true burst times random error exp(σZ), for nine values of σ from 0 (perfect) to 2, on W4 and W5 (python run_innovation.py --part noise, about 20 s). The same noisy predictions go to the full proposed mechanism and to plain SJF.

  • W4: with perfect predictions the mechanism waits 1,384 ms against 1,934 ms for SJF (−28.4%, 10/10 seeds). With the real model it waits 1,786 ms, so perfect predictions would still save 22.5%.
  • Real errors cost more than random ones. The model's measured error spread is σ = 1.25, but it performs like σ = 1.86 on the noisy-oracle curve, because real errors are systematic.
  • W5: the curve is flat (5,057 to 5,240 ms); with perfect predictions the mechanism is 9.0% worse than SJF (4,641 ms), so time slicing is the bottleneck there.

9.2 The adversarial workload W7 and the guard

W7 has 50% interactive, 20% I/O-bound and 30% bait processes. A bait process runs 10–20 bursts of about 1 ms, then one burst with a median of 400 ms, twice, then a few short bursts; the bait processes are 30% of the processes but 76% of the CPU demand (72–80% across seeds). It was designed to attack the scheduler, not to look like a normal system.

The guard lowers the average wait by 21.5% and interactive waiting by 92% (both on 10 of 10 seeds, significant). The bait processes pay: they wait 22% longer, and starved processes rise from 4.0 to 6.9. MLFQ still has the lowest average wait on W7 (9.3% below the guard), and the worst case with the guard is about twice that of RR-5 and MLFQ.

9.3 Cost of the guard elsewhere, and persistent ageing

On W1–W5 the guard changes the average wait by −1.8% to +0.1%, none significant after correction; on W6 it lowers it by 1.6%. The W4 worst case rises by 5.6% (not significant after correction). Separately, the ageing term restarts after every time slice: on the tuning seeds this discards 70% of the waiting on W4 (84% for the ten worst-off processes). A persistent version (Adaptive-ML-A, β = 0.01) improves W2 by 6.9%, but raises the average wait by 17.5% on W6 and 51.2% on W7, because the credit rewards the long bait bursts. It was not kept. The recommended configuration is Adaptive-ML-G.

9.4 Statistical validation

analyse_innovation.py compares configurations seed by seed: the change in the mean, a percentile bootstrap 95% confidence interval (10,000 resamples), the exact two-sided Wilcoxon signed-rank test, and a Holm correction within each family of related tests. With ten seeds the smallest possible p-value is 0.002. A result is called significant only if the Holm-corrected p is below 0.05; for example, the guard's +5.6% W4 worst case has unadjusted p = 0.027 but Holm p = 0.328, so it is not significant after correction.

  • Where it helps: mixed workloads, where short and long bursts compete. On W4 it beats every classical algorithm on average wait except SRTF-EMA (3% better on average, but 35% higher worst case and more switches).
  • Ageing is what controls the worst case: removing it doubles the worst wait on W5, and starved processes on W5 drop from 7.7 (SJF-EMA) to 0.2.
  • The adaptive quantum matters most for long bursts: fixing it at 10 ms on W5 costs 11% on average and 52% on worst case.
  • Prediction: 12–22% lower error than EMA on every workload, but better prediction alone (ML-predicted SJF) gains only 5% on W4. The benefit comes from using the prediction both for ordering and for the quantum.
  • Where it loses: all-I/O and all-interactive workloads have short random bursts with nothing to predict beyond the mean, so preempting at a small quantum only adds switches. Under overload, the waits are so long that ageing pushes the order towards FCFS.
  • Surprise: on W5, plain FCFS beats even the oracle on average wait. With many bursts per process, always running the shortest burst first starves processes in their long phase. The oracle is a strong reference, not an absolute lower bound.

13. Limitations and future work

  • Simulation only: one CPU, no caches or memory effects, no real kernel.
  • Synthetic workloads: the model is trained and tested on the same generator (different seeds), which is also why online refit showed no benefit.
  • A prediction takes about 0.5 ms in Python, far too slow for a kernel; a small decision tree or lookup table would be needed.
  • Linear ageing struggles under heavy overload; scaling it with the load is a natural fix. Making the credit persistent made things worse (Section 9.3).
  • The guard is tested only empirically and on one adversarial pattern that we designed (W7, also part of the tuning set on seeds 100–102). MLFQ still beats it on W7's average wait, and its W7 worst case is about twice that of RR-5 and MLFQ.
  • Next steps: real burst traces, moving the quantum controller into xv6, and multi-core scheduling.

14. Questions to be ready for

Why use machine learning at all?

Exponential averaging uses one feature and lags after phase changes. The model uses 12 features and is 12–22% more accurate. But the honest finding is that most of the gain comes from using the prediction twice, not from accuracy alone (Adaptive-EMA vs Adaptive-ML shows this).

How do you know the simulator is correct?

It reproduces textbook results exactly (17, 3, 5.67, 6.5 ms), every scheduler delivers the same total CPU time, event times never go backwards, and all 53 tests pass. Re-running the 11 original configurations also reproduces all 660 saved results exactly.

What if the prediction is wrong?

A wrong prediction only affects ordering and quantum; the process still runs. Ageing makes a long-waiting process go first eventually, the quantum uses observed error ratios, and the overrun guard stops a burst that has clearly outrun its prediction from being treated as short. Section 9 measures this directly.

Why not just use SRTF?

SRTF-EMA is 3% better on average on W4 but has a 35% higher worst-case wait and more switches, because it preempts whenever a newly ready process has a shorter predicted remaining time, and it has no ageing.

How did you avoid tuning to the test data?

The model was trained on seeds 1000–1004; β, the guard and persistent ageing were tuned on seeds 100–102; the evaluation used seeds 0–9. All the other parameters came from the original plan.

Why did you add the overrun guard?

Because a burst that outruns its prediction keeps its short estimate and is picked again after every quantum. On W7 this made the scheduler lose to Round Robin and MLFQ. The guard cuts W7's average wait by 21.5% and interactive waiting by 92%, with no significant change on W1–W5.

Isn't W7 designed to make the guard look good?

W7 is designed to expose the weakness, and the documents say it is adversarial. The guard still does not win everywhere on it: MLFQ has a 9.3% lower average wait and a much lower worst case. Its parameter was tuned on seeds 100–102 and the results come from seeds 0–9.

Why not keep persistent ageing?

It matches the stated intent better, but it raised average waits by 17.5% on W6 and 51.2% on W7, because it rewards long mispredicted bursts.

Why does it lose on I/O-bound workloads?

Bursts are short and random (exponential), so nothing can be predicted beyond the mean, and preempting at a small quantum adds context switches without improving the order.
